# CLAUDE.md – wp-dev-env

General Docker development environment for WordPress themes and plugins; only Docker is needed on the host. It is for development only: tests, release tests and benchmarks run in a separate test environment (e.g. [wp-test-env](https://github.com/saijsaij/wp-test-env)), never against this site. It lives next to the projects it serves (the parent directory is the workspace, mounted as `/workspace`; projects may be nested in it). Every project gets a site (own database, uploads and host `<site>.localhost`); one site runs at a time. The README is the user documentation; this file lists what matters when changing the environment.

## Rules

- **Stay general.** Nothing here refers to a specific theme, plugin or library: no project names in scripts, compose file, README or the example files. Projects are configured only in the local site files `sites/<site>.env`.
- **Never commit `config.env`, `sites/*.env`, `.env` or `data/`.** `.env` is generated by `scripts/setup` from `config.env` and the site file; never edit it. Every variable a script reads is documented in `config.env.example` or `sites/example.env.example` and explained in the README; keep them in sync, including the key lists in `scripts/setup`.
- **Latest stable WordPress, never beta:** the image uses the floating `php8.5-apache` tag; automatic core updates stay disabled.
- **WordPress core is never persisted:** `/var/www/html` is a tmpfs in the WordPress container; only `data/sites/<site>/db` and `data/sites/<site>/uploads` persist.
- **Live data never reaches a repository:** dumps and uploads of live sites live below `data/`; `scripts/import` refuses them inside any other Git work tree. The WordPress container has no database client: database work runs in the `db` container, file work in `tools`.
- **Sites never touch each other's data:** switching stops the active site first; `scripts/reset <site>` deletes only `data/sites/<site>`.
- **The workspace is read-only in `wordpress`;** only `tools` writes to it, as the host user (`HOST_UID`/`HOST_GID`).
- **Relative symlinks must resolve everywhere:** the structure below `/workspace` matches the host, on the host and in every container.
- **Scripts are idempotent and fail loudly:** `set -euo pipefail`, clear `ERROR:` messages naming the file, variable or project at fault, no silent fallbacks.
- Verify the behavior of images, Docker Compose and WP-CLI in their documentation or source before relying on it; say clearly when something is not verified.
- Everything in this repository is English; other repositories are linked by GitHub URL.

## Commands

Run from this directory.

```sh
scripts/setup <site>                                                   # idempotent: switch to the site, build, install, start, configure
scripts/reset <site>                                                   # delete the site's database and uploads, run setup again
scripts/import <site> <dump> [--uploads <dir|archive>]                 # replace the site's database (and uploads) with a dump
docker compose exec -u www-data wordpress wp <command>                 # WP-CLI
docker compose run --rm tools composer <command> --working-dir=/workspace/<project>
docker compose run --rm tools npm --prefix /workspace/<project> <command>
docker run --rm -v "$PWD:/mnt" -w /mnt koalaman/shellcheck:stable scripts/*   # after changing scripts
```

## Definition of done for changes

- `shellcheck` reports nothing for `scripts/*`.
- `scripts/setup <site>` succeeds twice in a row (second run changes nothing) and prints the running WordPress version; switching to another site and back leaves both sites' data unchanged; `scripts/reset <site>` restores the defined state of that site only.
- The services named in the README are reachable through Traefik (`WP_URL`, Mailpit, dashboard); loopback requests of WordPress work (`scripts/setup` checks them).
- README, `config.env.example`, `sites/example.env.example`, the key lists in `scripts/setup` and `compose.yaml` describe the same variables and services.
